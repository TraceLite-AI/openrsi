## 实际运行的协议

- 试次时间：北京时间 2026-11-03 21:32:22 至 2026-11-05 04:39:55。
- 三组：整包择优、最佳单项、正收益单项合并。没有额外运行原生 HyperAgents 对照组。
- 本地固定划分：50 train／19 gate／20 sealed，seed 0；未证明与论文未公开的原始划分相同。
- Terra；MiniSWE 固定起点 `388da74`，附带已记录的依赖/API 适配；评测 high、100 步、单题费用上限 3 美元、最多 4 题并行。
- 5 代；相同父版本、相同代共享证据。每代覆盖 50 道训练题，19 道题用于选择与复测。
- 固定提示＋直接 LLM 调用提案，**没有显式指定提案 reasoning_effort**，不是官方 Codex/xhigh HyperAgents 变异器。
- 只允许改 `mini.yaml` 和 `agents/default.py`，每个 hunk 最多增删 12 行。冻结两个各含两项修改的整包，按哈希选其中两个单项；最多合并两项。
- 使用 AnyRSI 组件和选择策略，由附带控制器编排并调用 RSIHub 原生评分接口；不是三个独立种子，也不是三份相同 token 花费的独立搜索。
- 锁定最终版本后，按 50／19／20 三批覆盖 89 题；相同最终版本共享评测。

AnyRSI 执行提交：`826439524d28406d7c76cdb528fc3ad470fdd487`。RSIHub 源码基线：`d6554299c58bf0fe2db04ddda0277f9db67ea680`。控制器和运行时另有记录中的适配，不能称为字节级官方复现。六个执行脚本/配置摘要均与运行时冻结值一致，见 `records.json` 的 `locked-protocol.json`。

## 首要问题：评分器启动失败被记成零分

对全部 **1,061 次物理任务评测**检查原始 verifier 日志：

| 阶段 | 明确出现只读 Python 目录错误 | 总试次 |
|---|---:|---:|
| 搜索阶段训练 | 110 | 250 |
| 搜索阶段准入、候选与复测 | 493 | 722 |
| 冻结后的最终评测 | 40 | 89 |
| 合计 | **643** | **1,061** |

643 次都包含 `Read-only file system` 和 `/opt/evolve/uv/python/`，且没有进入 pytest 测试阶段。**642 次被原运行器记为 `benchmark_complete`、reward=0**；另一次同时有 Agent 超时，两个分类不能直接相加。

最终评测的 50 道训练题有 22 道、19 道准入题有 13 道、20 道封存题有 5 道受影响。此外还有两道 API 策略拒绝。这个签名只识别已确认的故障，不能据此宣布其他零分都经过完整环境排查。

原因链有对应证据：

1. verifier 继承了 `UV_PYTHON_INSTALL_DIR=/opt/evolve/uv/python`，其容器挂载是只读；共享目录只有 Python 3.12。
2. 例如 `mteb-retrieve` 原始 `tests/test.sh` 使用 `uvx -p 3.13`。
3. 所需 Python 安装失败，测试未启动；脚本仍根据命令的非零退出状态写 `reward.txt=0`。
4. 运行器通常没有异常字段，控制器因而把这些零分当作可评分结果，覆盖检查没挡住。
5. 提案器收到零分和 Agent 轨迹尾部，没有收到 verifier 启动错误，于是对环境问题提出了格式核对等行为修改。

见 [逐试次日志审计](evidence/verifier-audit.json)与[环境证据](evidence/bootstrap.json)。**不能删除这些题再报“校正后的 benchmark 成绩”**，缺失的真实评分需要新实验。

此前小时汇报里的“无运行异常”只检查了运行器异常字段，没有核验评分器是否执行到测试阶段；这项执行检查不充分。

## 次要观察及其证据边界

**修改确实加载了。** 22 个不同候选全部只改 `mini.yaml` 的 `instance_template`，没有修改 Python 功能代码。532 条候选轨迹的配置与版本一致，渲染后的第一条用户消息包含全部新增文字。不能归因于“补丁没生效”。[输入核验](evidence/prompt-activation.json)

**提案主要是通用提醒。** 如检查换行、按要求执行命令、核实数据来源、验证最终产物。五代保留过 32 个原子提案，20 个进入整包，只有 10 个被单独测量。范围与覆盖有限，但在评分器失效时不能证明放宽范围一定有效。[实际补丁](patches/)

**表面收益集中在两个波动题。** 十次搜索期父版本准入测量中，`gcode-to-text` 通过 7 次，`portfolio-optimization` 通过 8 次；20 个初评候选分别通过 15 和 18 次。其余 17 题的父版本结果固定。14 道持续零分题没有被任何初评候选救回，其中 13 道正是经常未能启动评分器的题。因此不能把持续零分都解释成任务能力不足。

**没有积累搜索经验。** 三组一直继承版本 0。每代提案池重置，提示里的 `already_kept` 只包含本代编辑，没有前几代被拒绝的编辑及其实测效果；本轮没启用动量、元层提案器进化或权重更新。这描述的是执行的控制器，不是 AnyRSI 全部能力。

**验收过滤了未复现的表面提升。** 多数“多对一题”在父版本复测时消失。当前数据不能证明验收过严、误拒绝了真实改进。是否允许平分版本，需要在有效评分器上另做对照。

- Proposer **16 次 HTTP 尝试**，其中一次无 usage；已报告 **254,469 tokens**。没有把它与 Target 的逻辑调用数混称为总 HTTP 次数。
- 余额不足旧批次、单步 pilot、符号任务与 FlashRSI 均不计入。

## 下一步先恢复测量

1. 分离 Agent 与 verifier 的 Python 环境，使用题目要求的版本及可写安装目录，或预先验证精确解释器。不要把整个宿主共享目录改成可写来掩盖问题。
2. 模型调用前运行真实 verifier 健康检查，覆盖解释器和依赖引导，并用已知正确/错误产物验证判分路径；仅检查 Agent 安装成功不够。
3. 把已识别的 verifier setup failure 归为不可评分，覆盖不足就停止，不能当作普通训练负样本。
4. 新建协议、运行时指纹和结果目录。旧零分、日志和决定不变；不能挑失败项重跑后拼成提升。
5. 有效评测建立后，再分别检验机制性修改、完整证据、多样性和失败历史。

本次只做只读审计与记录发布，**没有启动新的付费实验**。
